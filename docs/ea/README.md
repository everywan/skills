# EA：在让 AI 写代码之前，先看懂系统将如何改变

EA（Engineering Analysis）是一个面向 AI Coding 的工程分析 Skill。

它位于 PRD 与 Spec / Plan 之间，帮助开发者在进入详细设计和代码执行前，先对齐问题边界、必要的系统约束、核心实现路径和关键取舍。

```text
PRD -> EA -> Spec -> Plan -> Coding
```

EA 不是一份压缩版 Spec，也不是提前展开的代码改动计划。它是一份可以快速评阅的开发草稿：内容足以支撑方案判断，又不会被接口字段、完整异常分支和上线细节淹没。

## 为什么需要 EA

AI 可以很快地给出方案和代码，但“完成了需求”不等于开发者真正理解了系统发生的变化：

- 需求在工程上到底意味着什么？
- 当前系统中哪些约束会直接影响方案？
- 最小可行的实现闭环是什么？
- 哪些复杂度是必要的，哪些只是理论上的完备？
- 哪些决策会改变业务语义、对外接口或数据模型？
- 哪些细节应该留到 Spec，而不是在草稿阶段过早展开？

EA 让 Agent 在执行前先阅读需求和代码，再把这些工程判断固化为一份短文档，让人保留对系统的理解和最终判断。

## 这个 Skill 会做什么

当你要求 Codex 编写或更新 EA 时，它会：

1. 阅读 PRD、需求澄清、已有设计文档和相关代码。
2. 用工程语言重新说明这次要解决的问题与边界。
3. 找出真正约束方案的系统事实。
4. 给出核心思想路径和最小闭环的设计草图。
5. 标出关键取舍、主要影响和仍需确认的问题。
6. 将接口、表结构、完整异常分支等细节明确留给 Spec。
7. 删除不影响方案判断的背景、重复结论和调研展示细节。

EA 通常应当让开发者在十分钟内完成评阅。

## 快速开始

### 安装

在本仓库根目录执行，单独安装 EA：

```bash
npx skills add ./ --skill ea --agent codex --global
```

Codex 通常会自动发现新安装的 Skill；如果没有出现，重启 Codex。关于 Skill 的加载位置和调用方式，可参考 [OpenAI Codex Skills 文档](https://developers.openai.com/codex/build-skills)。

### 使用

在 Codex 中显式调用：

```text
$ea 基于 docs/prd/order-cancel.md 写一份 EA，先对齐核心开发方案。
```

也可以直接用自然语言描述目标：

```text
基于这个 PRD 写一份 EA。
```

```text
先分析当前代码中的提交链路，再写 EA，不要展开成完整 Spec。
```

```text
更新现有 EA，压缩不影响方案判断的背景，只保留核心路径和关键取舍。
```

生成的文档默认写入：

```text
docs/superpowers/ea/YYYYMMDD-<topic>.md
```

Skill 不会默认执行 `git add`、提交代码或创建 PR。

## EA 的输出长什么样

EA 没有要求每份文档使用完全相同的章节。它通常围绕以下内容组织，并根据任务自由合并、删减和命名：

- 问题与边界
- 必要的现状约束
- 方案草图
- 待确认项与主要影响

一个核心设计草图可能是：

```text
现有提交链路
  -> 提交成功后触发
  -> 核心服务判断
  -> 规则 / 状态 / 幂等
  -> 写入目标状态
  -> 记录最小排查信息
```

它需要说明系统准备如何变化，但不会继续展开每个接口字段、表字段和失败分支。

## EA 与其他文档的区别

| 文档 | 核心问题 | 主要内容 |
|---|---|---|
| PRD | 为什么做、要解决什么问题？ | 产品目标、用户场景、需求范围 |
| EA | 这个需求在工程上意味着什么？ | 问题边界、系统约束、核心路径、关键取舍 |
| Spec | 最终要建设什么？ | 完整约束、接口、数据、状态、异常和验收标准 |
| Plan | 具体怎么执行？ | 代码任务、改动顺序和验证方式 |

EA 负责把需求转换成工程理解。方案已经清楚后，再由 Spec 完成正式设计，由 Plan 拆成代码改动。

## 什么情况下适合使用

适合先写 EA：

- 需求不大，但影响面还不明确。
- 需要先理解现有链路，再决定怎么改。
- 存在会改变业务语义、接口或数据模型的关键决策。
- AI 可以执行，但开发者还不能清楚解释为什么这样设计。
- 准备编写 Spec，希望先对齐核心思路并控制方案复杂度。

通常不需要写 EA：

- 文案、注释或配置值等纯机械修改。
- 影响范围清晰、容易回退的简单修复。
- 已经有完整、有效的设计文档，只需要按 Plan 执行。

EA 不是所有任务必须经过的流程。它的价值在于为需要工程判断的任务提供一个足够轻、又足够可靠的分析层。

## 写作边界

EA 应该包含：

- 用工程语言重述问题和边界。
- 直接约束方案的系统事实。
- 核心思想路径和最小闭环设计草图。
- 会改变方案判断的关键取舍。
- 主要影响点和预期系统行为。
- 仍需确认的问题。
- 明确留给 Spec 展开的细节。

EA 不应该包含：

- 完整的项目背景或调用链介绍。
- 只用于展示调研过程的方法名、表名和实现细节。
- 完整接口文档、表字段和状态机。
- 全量一致性论证和失败分支。
- 完整测试矩阵、监控、上线与回滚方案。
- 文件级代码改动计划。

核心原则是：先写最小闭环，只保留会影响方案判断的内容。
