# 在 PRD 和 Spec 之间，我增加了一层 EA
> 在让 AI 写代码之前，我们是否真的看懂了系统将如何改变？

使用 AI Coding 一段时间后，我遇到过一种很典型的情况：需求刚讲完，Agent 很快给出一份看起来完整的技术方案，接着开始改代码，测试也通过了。

但如果这时追问：

- 这次需求实际上改变了系统的哪条链路？
- 为什么选择这个方案？
- 新增的状态、表或 Worker 是否真的必要？
- 哪些风险已经接受，哪些细节只是暂时没有展开？

开发者不一定答得出来。

问题不在于 AI 没有完成任务，而在于从 PRD 到 Spec、Plan 和代码之间，缺少了一个让人重新建立工程理解的阶段。

因此，我在这条链路中增加了 EA：

```text
PRD -> EA -> Spec -> Plan -> Coding
```

EA 是 Engineering Analysis，即工程分析。这篇文章介绍它解决什么问题、为什么不能直接用一份 Prompt 代替，以及我如何把它做成一个 Codex Skill。

## 一、PRD 到 Spec 之间缺少什么

PRD 主要描述产品目标、用户场景和需求范围。Spec 则需要展开接口、数据、状态、异常、权限、验收和上线风险。

两者之间存在一个经常被忽略的问题：

> 这个需求放进当前系统以后，在工程上到底意味着什么？

如果这个问题没有先回答，Agent 往往会直接从需求文本推导出一套形式完整的设计。它可能没有读懂当前链路，可能把不确定性转化为新状态，也可能为尚不存在的问题设计迁移和兼容机制。

开发者随后面对的是一份细节很多的文档。逐项审查字段和异常分支很费时间，而最核心的方案判断反而被埋住了。

EA 的作用，就是在完整设计之前先建立一个更小的评审对象。

## 二、EA 到底是什么

EA 是一份开发草稿，用于固化开发者对需求的工程理解、核心思想路径和最小闭环设计。

它应该回答：

- 这次真正要解决的问题和边界是什么？
- 哪些现状事实会直接约束方案？
- 核心实现路径是什么？
- 哪些取舍会改变最终方案？
- 系统的主要行为将怎样变化？
- 哪些问题仍然需要用户确认？
- 哪些细节应该留给 Spec？

EA 不是压缩版 Spec，也不是文件级 Plan。

它不会为了显得完整而列出所有接口字段、表字段、状态流转、异常分支、测试矩阵、监控和回滚方案。只有当这些细节会影响关键取舍时，它们才应该提前出现。

我希望一份 EA 通常能在十分钟内完成评阅。超过这个范围时，首先应该删除背景介绍、重复说明和不影响方案判断的实现细节，而不是继续压缩字体或堆叠小标题。

## 三、一个简单例子

假设需求是：订单支付成功后，向用户发送权益到账通知。

一份过早进入 Spec 的方案，很容易马上讨论：

- 新建通知任务表及全部字段。
- 定义任务状态机。
- 设计消息队列和重试 Worker。
- 增加 Feature Flag。
- 补偿历史支付订单。
- 定义监控指标和告警。

这些内容不一定错误，但它们把许多尚未确认的问题提前固化成了设计。

EA 会先把问题收敛成一个最小闭环：

```text
现有支付成功链路
  -> 在既有事务完成后触发通知
  -> 复用现有通知服务
  -> 以支付单号作为幂等依据
  -> 记录最小的发送结果供排查
```

然后只保留真正会改变方案的问题：

- 现有通知服务是否已经提供可靠重试？
- 通知失败是否允许影响支付主流程？
- 是否存在必须补偿的历史订单？

如果现有服务已经提供异步投递和重试，就没有必要再设计一套任务表和 Worker。如果业务明确不补历史数据，也没有必要为不存在的迁移场景增加状态。

EA 不负责完成所有细节，而是先判断哪些复杂度真的需要进入 Spec。

## 四、这个 Skill 如何工作

我把 EA 的写作边界做成了一个 instruction-only Skill。它不依赖 MCP 服务，也不调用额外 API，核心是约束 Agent 的分析和写作过程。

当用户要求编写或更新 EA 时，Skill 会要求 Agent：

1. 阅读 PRD、需求澄清、已有设计文档和相关代码。
2. 用自己的工程语言重述问题，而不是改写原始需求。
3. 检查当前系统链路，避免凭空设计。
4. 找出直接影响方案判断的系统事实。
5. 写出核心思想和最小闭环设计草图。
6. 标出关键取舍、影响点和待确认问题。
7. 把 Spec 级细节明确延后。
8. 做一次删除式自查。

删除式自查尤其重要。它会主动删除：

- 不影响方案判断的现状介绍。
- 已经在其他位置表达过的结论。
- 只用于证明“调研很充分”的方法名、表名和代码细节。
- 没有真实分歧的备选方案。

很多 AI 文档的问题不是遗漏，而是过量。通过增加明确的删除动作，EA 才能保持开发草稿的粒度。

## 五、为什么做成 Skill，而不是保存一段 Prompt

一段 Prompt 当然也能要求 AI 写工程分析，但 Skill 有几个更适合团队复用的特点。

首先，它有明确的触发条件。用户可以显式调用 `$ea`，Codex 也可以在任务与描述匹配时识别这套工作流。

其次，Skill 把详细流程和写作边界放在独立的 `SKILL.md` 中，不需要每次把完整提示词贴进对话。

再次，它可以和仓库级规则共同工作。Agent 仍然会读取项目的 `AGENTS.md`、代码和已有文档，EA Skill 只负责补充这一类任务的专门工作流。

最后，Skill 本身可以版本化。写作边界、触发条件和删除规则发生变化时，可以像代码一样评审和演进，而不是散落在个人收藏的 Prompt 中。

## 六、什么时候应该使用 EA

适合先写 EA：

- 需求边界看起来清楚，但代码影响面不明确。
- 需要先理解现有链路，再决定怎么改。
- 存在会改变业务语义、接口或数据模型的决策。
- AI 可以立即执行，但开发者还不能清楚解释方案。
- 准备写完整 Spec，希望先确认核心路径并控制复杂度。

通常不需要 EA：

- 文案、注释和配置值等纯机械修改。
- 影响范围清楚、容易回退的简单修复。
- 已经有完整且仍然有效的设计，只需要按 Plan 执行。

EA 不是新的流程税。它应该只在工程判断的收益高于文档成本时出现。

## 七、安装和使用

在 Skills 仓库根目录执行，单独安装 EA：

```bash
npx skills add ./ --skill ea --agent codex --global
```

完整说明见 [EA 使用说明](../README.md)。

安装后可以显式调用：

```text
$ea 基于 docs/prd/order-cancel.md 写一份 EA，先对齐核心开发方案。
```

也可以使用自然语言：

```text
先分析当前代码中的提交链路，再写 EA，不要展开成完整 Spec。
```

默认输出位置是：

```text
docs/superpowers/ea/YYYYMMDD-<topic>.md
```

Skill 不会默认执行 `git add`、提交代码或创建 PR。

## 八、当前边界和下一步

当前版本是 `0.1.0`，主要使用简体中文，首先面向 Codex。它目前只提供 EA 的分析和写作工作流，不试图替代 PRD、Spec、Plan 或完整的工程流程框架。

接下来更重要的工作不是继续增加规则，而是收集真实使用样例：

- 哪些任务通过 EA 提前发现了影响面？
- 哪些过度设计在 Spec 之前被删除？
- 哪些关键问题确实需要由人确认？
- 哪些内容仍然容易膨胀成 Spec？

这些反馈会比继续抽象模板更有价值。

## 结语

我做 EA Skill，不是为了让 AI 再多生成一种文档，而是为了在 AI 快速执行之前，保留一个让开发者理解和判断的空间。

它希望解决的是一个很朴素的问题：

> 在让 AI 写代码之前，我们是否真的看懂了系统将如何改变？

如果你也在使用 Codex 处理真实项目，欢迎试用并分享你的 EA 样例、边界问题和改进建议。
