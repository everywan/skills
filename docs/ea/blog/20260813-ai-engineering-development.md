# AI Coding 的核心问题不是 Prompt：一套 AI 工程化开发方法

刚开始使用 AI Coding 时，我们很容易把注意力放在 Prompt 上：怎样描述得更清楚，怎样让 AI 一次生成正确代码，怎样找到一个“万能提示词”。

但当 AI 真正进入日常开发后，我越来越确定：AI Coding 的核心问题不是 Prompt，而是工程体系。

AI 可以快速写出代码，却不一定理解系统；可以完成局部任务，却不一定知道影响面；可以给出看起来完整的方案，却可能让开发者逐渐失去对系统的工程判断。

真正需要解决的问题是：

```text
如何让 AI 在正确上下文里，按正确流程，完成正确粒度的工程任务？
```

这篇文章整理的是我目前对 AI 工程化开发的一套理解。它不是要求所有任务都走一遍重流程，而是试图回答：AI 参与开发以后，哪些能力仍然必须由软件工程体系提供？

## 一、Prompt 只是入口

Prompt 当然重要。它决定了我们如何表达当前目标，也会影响单次输出的质量。

但 Prompt 解决不了这些问题：

- AI 是否知道项目过去为什么这样设计？
- 当前需求会影响哪些模块、数据和状态？
- 团队有哪些不能突破的业务和工程约束？
- 这个任务应该直接改代码，还是先写方案？
- 实现完成后，怎样证明结果可信？
- 这次获得的知识，怎样避免下次重新调研？

把这些责任都塞进一个越来越长的 Prompt，最终只会得到一份难以维护、难以复用的临时上下文。

我更倾向于把 AI 工程化开发理解成一条能力链：

```text
Knowledge
  -> Context
  -> Workflow
  -> Agent
  -> Execution
  -> Review / Verification
  -> Knowledge Update
```

Prompt 是这条链路的入口，却不是整条链路本身。

## 二、这条能力链分别解决什么问题

### Knowledge：项目已经知道什么

Knowledge 是可持续复用的项目知识，包括架构约束、业务规则、历史决策、开发规范和已经验证过的解决方案。

没有这一层，AI 每次都要重新阅读和猜测。它也许能得到一个局部正确的答案，却很难稳定地符合项目长期积累下来的约束。

### Context：当前任务需要知道什么

项目知识不应该全部进入一次对话。Context 的任务，是从 Knowledge 和代码中选出当前任务真正需要的部分。

上下文太少，AI 会凭空补全；上下文太多，关键信息又会被噪声淹没。Context Engineering 的重点不是“给得越多越好”，而是让信息与当前任务匹配。

### Workflow：AI 应该怎样工作

Workflow 约束执行顺序和检查点，例如：

```text
分析 -> 设计 -> 拆解 -> 实现 -> Review -> Verification
```

它解决的不是模型会不会写代码，而是模型是否会在影响面不清楚时停下来分析，是否会在实现偏离方案时回退，是否会在完成前验证结果。

### Agent：谁承担哪一类工作

Agent 是在上下文和流程约束下承担任务的执行者。它可以负责调研、实现、评审或验证。

Multi-Agent 也在这一层，但它不应该成为默认入口。只有当任务范围大、需要多个独立视角，或者子任务确实能够并行时，多 Agent 才能带来收益。没有清晰的上下文和边界，多 Agent 只会放大混乱。

### Review / Verification：结果为什么可信

“代码已经生成”不是完成标准。完成意味着我们能说明：

- 需求行为已经实现。
- 原有行为没有被意外破坏。
- 关键边界得到验证。
- 风险和未覆盖部分已经明确。

对于复杂任务，实现者与评审者最好保留一定程度的视角独立，避免让实现过程本身成为正确性的唯一证据。

### Knowledge Update：这次工作留下了什么

一次开发任务不应只留下代码。重要的工程判断、踩过的坑和稳定规则，应该重新沉淀回 Knowledge 或 Workflow。

否则下一次任务仍然要从头调研，AI 带来的速度也很难真正复利。

## 三、EA、Spec 和 Plan 解决的是不同问题

在这套能力链中，我把开发前的文档进一步拆成了三个层次：

```text
PRD -> EA -> Spec -> Plan -> Coding
```

它们不是同一种文档的不同长度版本，而是在回答不同的问题。

| 文档 | 核心问题 | 主要内容 |
|---|---|---|
| PRD | 为什么做、要解决什么问题？ | 产品目标、用户场景、需求范围 |
| EA | 这个需求在工程上意味着什么？ | 问题边界、系统约束、核心路径、关键取舍 |
| Spec | 最终要建设什么？ | 完整约束、接口、数据、状态、异常和验收标准 |
| Plan | 具体怎么执行？ | 代码任务、改动顺序和验证方式 |

这里新增的 EA，是 Engineering Analysis，即工程分析。

它位于 PRD 和 Spec 之间，目标不是完成正式技术设计，而是让开发者先建立工程理解：当前系统怎样工作，这次真正要改变什么，最小闭环是什么，哪些决策会显著改变最终方案。

EA 的价值在于防止流程从“读完需求”直接跳到“让 AI 写一份完整方案”或“让 AI 开始改代码”。这个跳跃看似节省时间，实际很容易让系统理解和方案判断一起交给模型。

## 四、四条核心原则

### 1. 轻重匹配

不是所有任务都需要完整文档和复杂流程。

```text
小任务轻流程
中任务要 Plan
大任务要 Spec
复杂任务才 Multi-Agent
```

机械修改如果强行写 Spec，只会制造流程负担；跨模块需求如果直接进入代码，又会丢失系统判断。

流程的价值来自匹配风险，而不是来自步骤数量。

### 2. 最小充分设计

技术方案应该选择满足当前需求的最小充分设计。

设计时优先复用已有数据模型、唯一约束、事务、幂等机制、组件和发布流程。在引入新表、状态机、Worker、Feature Flag 或抽象层之前，至少要回答：

1. 它解决的具体问题是什么？
2. 这个问题是否真实存在于当前系统？
3. 已有机制为什么不能解决？
4. 不引入它会发生什么实际错误？

无法证明必要性的复杂度，不应该因为“以后可能有用”就进入当前方案。

### 3. 人保留工程判断

AI 可以查调用链、写代码、拆任务和执行验证，但开发者至少要能解释：

- 为什么这样设计？
- 哪些链路会变化？
- 哪些风险被接受？
- 哪些细节被延后？
- 出问题时先从哪里排查？

如果功能完成以后，开发者只能复述 AI 给出的结论，却无法解释系统变化，那么流程仍然是不完整的。

### 4. 允许回退和升级

任务规模不是在开始时判断一次就永远不变。

当实现中发现需求不完整、影响面扩大、原方案无法落地，或者测试暴露出新的系统约束时，应该回到 EA、Spec 或 Plan 更新判断，而不是继续让 AI 沿着错误方向完成更多代码。

稳定的工作流必须允许回退，也必须允许从轻流程升级到重流程。

## 五、按任务规模选择流程

我目前使用的默认路由是：

| 任务规模 | 默认流程 | 说明 |
|---|---|---|
| Tiny / Bug | Codex | 上下文小、风险低，直接执行 |
| Small | EA-light -> Codex | 快速确认目标和影响范围 |
| Medium | EA -> Plan -> Codex | 先理解影响面，再拆执行步骤 |
| Large | EA -> Spec -> Minimality Review -> Plan -> Codex | 形成正式方案，再删除不必要复杂度 |

这不是必须机械执行的工时公式。跨模块、长期维护、多人协作、高上线风险，以及涉及状态机、数据一致性或权限边界的任务，都应该提高流程强度。

Multi-Agent 则是另一条轴：它取决于任务是否需要分工、独立视角和并行，而不是只取决于开发时间。

## 六、为什么还需要开发者写 EA

有人可能会问：既然 Spec 也可以由 AI 生成，为什么还要多一个 EA？

因为 EA 的目标不是增加一份文档，而是建立一个短暂但明确的工程判断阶段。

一份好的 EA 应该足够短，让开发者可以快速评阅；又足够具体，能说明核心路径和真正的取舍。它不应该展开完整接口、表结构、异常矩阵、监控和上线方案，这些属于 Spec。

EA 更像开发者与 Agent 共同确认的一份基准草稿：

```text
我们理解的是不是同一个问题？
我们看到的是不是同一组系统约束？
这个核心方案是否值得继续展开？
```

只有这三个问题基本对齐，后面的 Spec、Plan 和 Coding 才有稳定基础。

## 七、从哪里开始实践

不需要一次性建设完整平台。可以从一个真实需求开始：

1. 让 Agent 先阅读 PRD 和相关代码。
2. 要求它只输出问题边界、必要约束、核心路径和关键取舍。
3. 人工删除不影响方案判断的背景和细节。
4. 根据影响面决定直接执行、写 Plan，还是继续展开 Spec。
5. 完成后把新发现的稳定规则沉淀回项目知识。

关键不在于文档名称，而在于不要把“理解、判断、执行、验证”压缩成一次无法审查的模型调用。

## 结语

AI Coding 正在让代码生成变得越来越便宜。与此同时，系统理解、工程判断和结果验证会变得更重要，而不是更不重要。

Prompt 会继续演进，模型能力也会继续提高。但只要我们仍然在建设需要长期维护的软件，就需要一套机制确保 AI 知道项目是什么、当前任务意味着什么、应该按什么流程工作，以及结果为什么可信。

这就是我理解的 AI 工程化开发：

> 不是让 AI 写更多代码，而是让 AI 在工程体系中完成正确的工作。
