# EA

EA 是 PRD 和 spec 之间的开发草稿，用来记录开发者理解需求后的核心工程思路和设计草图。

EA 不负责兜全细节。详细接口、表结构、状态机、权限、测试、上线、监控和回滚由 spec 兜底。

## 流程位置

使用顺序：

```text
PRD -> EA -> Spec -> Plan
```

- PRD：澄清产品目标和需求问题。
- EA：固化工程理解、核心思想路径和核心设计草图。
- Spec：展开为可技术评审的完整方案，兼顾产品、测试、前端、后端、兼容性和上线风险。
- Plan：拆成具体代码改动和任务执行步骤。

## 输出位置

在当前项目下创建或更新 EA：

```text
docs/superpowers/ea/YYYYMMDD-<topic>.md
```

不要写死其他项目的绝对路径。

不要执行 `git add`、暂存、提交或创建 PR，除非用户明确要求。

## EA 应该包含

下面是内容检查清单，不是章节清单。不要为了覆盖清单逐项建立章节；一条结论只出现一次，放在最能支撑方案判断的位置：

- 用工程语言重述问题和边界
- 会直接约束方案的现状事实
- 核心思想路径和最小闭环设计草图
- 会改变方案判断的关键取舍
- 主要影响点和预期系统行为
- 仍需用户确认的问题
- 明确留给 spec 展开的细节

可以优先考虑以下组织方式，但它不是固定章节模板。应按任务内容自由命名、合并或删减，不需要凑齐四段：

1. 问题与边界
2. 必要的现状约束
3. 方案草图
4. 待确认项与主要影响

已确认结论直接融入正文，不建立“已确认事项汇总”。只有确实自成一体的需求点或技术决策可以单列。待确认项只保留仍会改变业务语义、对外接口、数据模型或关键方案选择的问题。

## 写作边界

EA 要写：

- 用工程语言重述需求
- 直接约束设计的当前系统事实，不设固定数量，只保留会影响方案判断的内容
- 核心思想路径
- 能说明最小闭环的核心设计草图
- 主要模块和职责
- 关键取舍
- 主要影响点
- 预期系统行为
- 明确哪些细节交给 spec

EA 不要写：

- 项目背景介绍或完整调用链
- 仅用于展示调研过程的方法名、表名和实现细节
- 完整接口文档
- 完整表字段
- 完整状态机细节
- 全量一致性论证
- 完整测试矩阵
- 监控、上线、回滚细节
- 文件级代码改动计划

## 核心设计粒度

EA 必须包含核心设计，但只写到草图层。

方案先写最小闭环。接口、字段、锁、索引、游标、任务状态和异常分支，只有在它们会影响关键取舍时才出现；其余交给 spec。

好的 EA 核心设计示例：

```text
现有提交链路
  -> 提交成功后触发
  -> 核心服务判断
  -> 规则 / 状态 / 幂等
  -> 写入目标状态
  -> 记录最小排查信息
```

不好的 EA：

- 列出每个表字段
- 写完整接口 request / response
- 展开所有失败分支
- 写成压缩版 spec

## 执行流程

1. 阅读 PRD、需求澄清、已有 spec、代码或用户上下文。
2. 用自己的工程语言说明“这次到底要解决什么”。
3. 检查当前系统相关链路，避免凭空设计。
4. 写出核心思想和核心设计草图。
5. 标出关键取舍和主要影响点。
6. 把细节明确留给 spec。
7. 做删除式自查：
   - 删除不影响方案判断的现状介绍。
   - 删除已经在其他位置表达过的结论。
   - 删除只是证明“调研很充分”的实现细节。
   - 删除没有真实分歧的备选方案。
8. 最后检查：这还是开发草稿吗？如果像技术方案评审稿，就继续删减 spec 级细节。

EA 通常应控制在开发者十分钟内可以完成评阅的篇幅。超出时，先压缩现状介绍、重复说明和不影响关键取舍的实现细节，不机械限制字数。
